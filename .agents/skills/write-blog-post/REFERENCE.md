# 技术博文反 AI 写作与工程师语调指南

本指南系统梳理技术博客写作中常见的 AI 写作特征，提供具体的识别标准与改写方案，帮助产出自然、专业、可信的技术内容。

---

## 常见 AI 写作模式与治理准则

### 1. 虚假区间与宏大叙事（False Range & Hollow Scope）
* **AI 典型特征**：喜欢用“从……到……”构筑虚假的全景感，如“从底层原理到架构实战”、“从基础语法到企业级最佳实践”、“全面剖析……涵盖 A、B、C 与 D”。
* **问题本质**：试图用宏大叙事掩饰内容的空洞或平庸，给读者造成过度承诺的印象。
* **改写准则**：直接陈述文章具体讨论的技术要点和实施边界。
  * ❌ *“从原理剖析到实战部署，全面掌握 Docker 容器化最佳实践”*
  * ✅ *“Docker 生产部署配置：多阶段构建与 Nginx 静态托管实践”*

### 2. 公式化三段式导言（Formulaic 3-Tier Intros）
* **AI 典型特征**：
  1. 行业/背景铺垫（“在当今快速发展的微服务/前端/云原生领域……”）；
  2. 选型吹捧（“X 凭借其强大的生态与极高的性能，成为业内不二之选/黄金搭档……”）；
  3. 矛盾宣布（“然而在实际业务落地中，往往面临诸多挑战……本文将系统梳理……”）。
* **问题本质**：无意义的“垫话”浪费读者时间，缺乏真实的业务上下文。
* **改写准则**：直接陈述真实痛点、触发场景与核心制约因素。
  * ❌ *“在现代前端协同办公领域，富文本编辑器扮演着至关重要的角色。Tiptap 凭借其高度可扩展性备受青睐。然而在多人实时协同中面临着冲突处理等痛点。本文将系统阐述……”*
  * ✅ *“在实现多人协同富文本编辑时，如果直接用传统 REST 接口同步内容，高频并发输入会导致光标跳跃和文本相互覆盖。本文讨论引入 Yjs CRDT 进行状态收敛的落地方案。”*

### 3. 浮夸营销大词与绝对化断言（Hype Words & Absolutes）
* **AI 典型特征**：滥用未经度量的修饰词（如“极致丝滑”、“彻底杜绝”、“降维打击”、“工业级神器”）。
* **问题本质**：工程师崇尚可测量、有边界的事实，绝对化断言显得极度不真实且不专业。
* **改写准则**：用具体指标、范围限定或客观事实说话。

| 禁用词 / AI 常用浮夸词 | 替代方案 | 示例 |
| :--- | :--- | :--- |
| **极致丝滑 / 丝般顺滑** | 低延迟、流畅度提升、交互即时 | “实现 60fps 拖拽渲染” |
| **彻底杜绝 / 彻底解决** | 显著减少、避免常见、拦截 | “避免未捕获的运行时异常” |
| **不二之选 / 黄金搭档** | 常见搭配、主流选型、适合场景 | “React 结合 TanStack Query 的常见方案” |
| **降维打击 / 工业级神器** | 成熟方案、特定优势、专用工具 | “适合高频状态变更的 CRDT 算法” |
| **甜点位 / 银弹** | 合理折中、性价比高的配置 | “兼顾内存占用与吞吐的折中参数” |
| **全面解析 / 深度复盘** | 梳理、记录、分析、实践总结 | “状态机驱动的复杂表单设计” |
| **不可或缺 / 重中之重** | 关键环节、核心模块 | “鉴权与数据一致性校验” |

### 4. 机械句式与列表过度加粗（Robotic Parallelism & Over-bolding）
* **AI 典型特征**：
  - 滥用否定式排比：“不仅……而且……”、“既能……又能……”。
  - 滥用破折号与设问句：“——这正是我们需要的”、“究竟该如何选择？”。
  - 列表每一个条目都强行采用统一格式：`- **四字名词**：解释内容……`。
* **改写准则**：
  - 混合句型长短，多用因果逻辑连接（“因为……导致……”、“考虑到……因而选择……”）。
  - 自然排版，不必给每一项机械添加粗体冒号，让内容本身表达层级。

### 5. 口号式升华总结 vs 工程经验小结
* **AI 典型特征**：
  - 文章结尾必然出现 `## 总结`；
  - 内容多为 3 条整齐划一的喊口号（“1. 坚决采用... 2. 榨干每一点潜力 3. 拥抱未来技术趋势”）。
* **改写准则**：
  - 标题改为 `## 工程经验小结` 或针对性的特定结语；
  - 内容聚焦**真实的架构权衡（Trade-offs）**、**不适用场景**与**防坑建议**。
  - 明确指出：“什么情况下不要用这套方案”、“维护成本在哪里”、“可能牺牲了什么”。

## 工程师真实语感注入法则

要写出让技术同行信服的内容，除了删除不良模式，还需注入一线工程师的思考特质：

1. **承认技术复杂性与不完美**：没有任何架构是完美的。“引入这套方案解决了实时性，但代价是客户端初始包增大了 200KB”比“完美兼顾了体积与速度”更让人信服。
2. **适度使用第一人称经验视角**：“在排查弱网重试时我们发现……”、“起初我们尝试了方案 A，但在并发超过 50 时遇到了死锁……”。
3. **给出边界条件与数字证据**：给出确切的耗时（ms）、体积（KB/MB）、版本号与配置参数，而不是泛泛的“快了很多”。
4. **保留必要的“技术锋芒”与直接判断**：如果某个方案在特定场景下就是糟糕的设计，直截了当说清楚为什么，无需左右摇摆的客套话。
